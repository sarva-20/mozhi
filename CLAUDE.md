# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is
Mozhi is a **non-generative phonetic correction layer** for domain-specific STT output. It sits between an STT engine and a downstream app and fixes mistranscribed domain terms with Metaphone + Jaro-Winkler + token-sort-ratio scoring in a sliding-window match. It is a UG capstone (KPRIET, Dept. of CSBS) plus a conference paper submission.

**Core rule, non-negotiable:** zero model inference, zero GPU, zero fine-tuning in the correction path. Every design decision must preserve this. (LLMs/models may be used only in tooling and eval scripts outside `app/`.)

## Commands
Run everything from the repo root. `tests/` and `scripts/` import `app.*` and `tests.*`, so scripts need `PYTHONPATH=.`.
- Setup: `python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`. Add `-r requirements-benchmark.txt` for the benchmark and transcription scripts. It is kept separate on purpose and is not used by the Docker image.
- Tests: `pytest` (currently 774 passed, 1 skipped, 1 xfailed: the known "Em, Dee, are" name collision; no batch case is xfailed) · single test: `pytest tests/test_pipeline.py::test_name` · one batch case: `pytest tests/test_batch_cases.py -k "<substring>"`
- Serve: `uvicorn app.main:app --reload` (endpoints: `GET /health`, `POST /correct {text, threshold?}`)
- Docker: `docker build -t mozhi . && docker run -p 8000:8000 mozhi`. The image copies only `app/` and `data/`.
- Live demo (Review 2): `pip install -r requirements-demo.txt && streamlit run streamlit_app.py`. Mic (`st.audio_input`), upload, recorded samples from `data/volunteer_audio/`, or typed text -> Whisper (`scripts/evaluate_accuracy.Transcriber`, reused) -> `correct_text()`, showing raw vs corrected transcript with changed words highlighted, a matches table, and the correction latency as the hero number (Whisper time is shown separately and labelled). Non-UI logic is in `demo/core.py` (outside `app/`, so it never ships in the Docker image); `requirements-demo.txt` is separate from `requirements.txt` on purpose. Streamlit is pinned to 1.56.0 because newer releases pull starlette 1.x, which conflicts with `fastapi==0.115.0`. `tests/test_streamlit_app.py` drives the real script through AppTest with a fake Whisper; `MOZHI_REAL_WHISPER=1 pytest tests/test_streamlit_app.py -k real_whisper` runs the real model. The mic widget itself cannot be driven by AppTest. `st.audio()` in the Samples picker needs an explicit `format=` mimetype (`demo.core.mimetype_for_suffix`) - `format=None` crashes deep in Streamlit's media file manager instead of guessing; only surfaced once a non-`.m4a` sample existed (the staged `.mp3` volunteer recordings), since every sample before that was `.m4a`.
- Try the pipeline: `python -m app.pipeline` (prints sample corrections with per-span scores and latency). `app/scorer.py`, `app/tokenizer.py`, `app/dictionary.py`, `app/acronym_map.py`, `app/letter_composer.py` and `app/morphology.py` each have a runnable `__main__` demo (run them with `PYTHONPATH=. python -m app.<module>`).
- Evidence scripts (each writes or feeds `reports/`):
  - `PYTHONPATH=. python3 scripts/latency_benchmark.py`
  - `PYTHONPATH=. python3 scripts/no_model_inference_proof.py` writes `reports/no_model_inference_proof.txt`.
  - `PYTHONPATH=. python3 scripts/comparison_benchmark.py` needs `HF_TOKEN` and optionally `HF_MODEL`.
  - `PYTHONPATH=. python3 scripts/collision_check.py candidates.json` reports collisions of candidate terms against `data/common_english_words.txt`.
  - `PYTHONPATH=. python3 scripts/transcribe_local.py <audio_or_dir>` runs faster-whisper on CPU, needs ffmpeg, and writes `data/stt_transcripts/*.json`.
  - `PYTHONPATH=. python3 scripts/dictionary_coverage.py [--workers N] [--terms a,b] [--out-dir D]` is the full-dictionary coverage test (~20 s): ~3.2k rule-generated mis-transcriptions across all 319 terms, each run through `correct_text()` in a carrier sentence, writing `reports/dictionary_coverage_{variants,terms}.csv` and `_summary.txt`. **It is SYNTHETIC: it measures robustness to what the operators imitate, not real STT accuracy, and must never be quoted as the accuracy number** (that needs real recordings, `evaluate_accuracy.py`). Recovery is scored word-level, case/punctuation-insensitive. `canonical`, `acronym_map` and `phrase_alias` variants are ~100% by construction and excluded from the headline. Deterministic (CRC32-ordered, no RNG). Current numbers and leads (see the summary): synthetic recovery 73.1% micro / 71.0% macro; hyphenated phrase terms recover 48.3% vs 72.4% for plain ones, and hyphen-normalizing the term string would newly clear the threshold for 79 of 109 missed variants (scoring-only estimate, false positives unmeasured); spoken digits (WPA2, IPv4...) and all-ambiguous letter spellings (CPU, TCP, ARP...) are unreachable by composition by design. This run originally found 6 terms whose CANONICAL form (spoken with zero errors) was altered by Mozhi - a pipeline defect, not a coverage gap - now fixed; see the DP fix and `NEVER_MATCH_PAIRS` entries below and `tests/test_dp_fragmentation.py`. Three of those six (`TCP handshake`, `configuration management database`, `web application firewall`) still have a 0/10 synthetic-corruption recovery rate, unchanged by the fix: a separate, pre-existing fuzzy-recovery gap, pinned as a known limitation, not silently absorbed into the headline.
  - `PYTHONPATH=. python3 scripts/evaluate_accuracy.py [--retranscribe]` is the repeatable accuracy evaluation. Every `data/volunteer_audio/<name>.m4a` paired with a human-written `<name>.expected.txt` is scored: raw STT WER vs Mozhi-corrected WER (word-level, rapidfuzz alignment), one CSV row per error region, and the catch-rate within the `phonetic_substitution` category (the addressable number). `category_suggested` requires BOTH Metaphone similarity >= 0.80 AND domain relevance (`is_domain_relevant`: the expected word(s) are, or contain, an actual word from a dictionary term, excluding `FUZZY_STOPWORDS`); phonetically-close-but-irrelevant regions ("that" -> "the") are labelled `out_of_scope` instead, so they don't dilute the headline number. It writes `reports/accuracy_evaluation.csv` and `reports/accuracy_evaluation_summary.txt`. Cached transcripts are reused unless stale or `--retranscribe`. Hand corrections go in `category_reviewed`, take precedence in the summary, and survive re-runs. Volunteer audio is excluded from the Docker image via `.dockerignore`. See `data/volunteer_audio/README.md`. On the full 32-file set (`test_audio1`/`2` plus 30 staged volunteer recordings, `vol01_crud`..`vol30_json`): raw WER 24.5%, corrected WER 24.7% (was 25.4% before the morphology-guard fix below), phonetic-substitution catch rate 5/35 = 14.3% domain-aware (was a diluted 2.6% before the `out_of_scope` split - 155 of 190 originally-"phonetic" regions were generic STT noise unrelated to the dictionary), 5 regressions remaining (all are `read`->RAID or `catch`->cache, deliberately unfixed - see below).

## Architecture
`app/main.py` (FastAPI, deliberately thin) → `app/pipeline.py::correct_text()`. All logic lives in `pipeline.py` and stays framework-agnostic. Do not add logic to `main.py`.

`correct_text()` runs in three steps:
1. **Score every span.** `tokenizer.py` yields tokens with char offsets. For every (start, window length ≤ `max_window`) pair, it produces at most one candidate, tried in this **priority order** (first hit wins, the rest are skipped):
   1. `acronym_map.ACRONYM_PHONETIC_MAP`: exact, hand-enumerated spoken forms ("ess ess dee" → SSD). Score 1.0, method `acronym_map`.
   2. `acronym_map.PHRASE_ALIASES`: exact multi-word mishearings backed by real recordings ("one link" → "WAN link"). Score 1.0, method `phrase_alias`.
   3. `letter_composer`: composes runs of spoken letter-sounds ("vee ell ay en") into a string and accepts it only on **exact** match against an `is_acronym` dictionary term. Score 1.0, method `letter_composed`. Never fuzzy.
   4. `scorer.combined_score` against every dictionary term, method `fuzzy`. The weights are 0.40 metaphone, 0.35 Jaro-Winkler and 0.25 token-sort, and they must sum to 1.0 (asserted at import). A candidate must reach `DEFAULT_THRESHOLD` (0.88).

   Hand-verified entries (1, 2) outrank derived ones (3) so a hand entry is always an effective override. Exact methods (1–3) all outrank fuzzy.
   - `max_window` is the longer of the longest dictionary term and the longest acronym-map key. The composer has its own `MAX_LETTER_WINDOW` (6) and runs as a **pre-pass** in `pipeline.py`, deliberately not through `max_window`: widening `max_window` also widens the fuzzy loop, which costs ~31 ms per extra level. Composed spans wider than `max_window` are inserted after the loop, guarded by `window_len > max_window` so they can never overwrite a higher-priority result.
2. **DP over token positions**, which is weighted interval scheduling. It picks the non-overlapping spans maximizing `(exact_tokens_covered, score_sum)` **lexicographically**, not raw score alone. `exact_tokens_covered` counts tokens under a match that is exact by construction (`acronym_map`/`phrase_alias`/`letter_composed`) or a fuzzy match scoring exactly 1.0 (the candidate is verbatim the term). This is not greedy left-to-right: greedy breaks on STT word reordering ("address IP" vs "IP address"). Why two keys instead of one: score is per-*match*, not per-*token*, so a 1-token exact match and a 5-token exact match both contribute 1.0 - fragmenting a correctly-spoken multi-word term into `{sub-word -> itself, 1.0} + {remainder -> a genuine partial-phrase fuzzy match against the full term, <1.0 but >= threshold}` could always outscore the one correct exact match under pure score-sum, e.g. "SQL"(1.0)+"injection"->"SQL injection"(0.887)=1.887 beating the exact 2-word match at 1.0 - producing "SQL SQL injection". The full-dictionary coverage test found six such cases; the exact-tokens-first comparison fixes five of them (a single verbatim span covering N tokens can never lose to a fragmentation verifying fewer than N of them, whatever its raw score). It generalizes the old tie-break (prefer the longer exact-match span on a literal numeric tie) to the general case where the fragmented total is strictly higher. See `tests/test_dp_fragmentation.py` for the full trace and the one case (below) it doesn't reach.
3. **Splice** replacements into the original string right-to-left using the char offsets.

False-positive guards, all tuned against real collisions:
- `FUZZY_STOPWORDS` in `pipeline.py`: windows made entirely of these are never fuzzy-scored. Jaro-Winkler inflates on short strings ("is" vs "ISP").
- `NEVER_MATCH_PAIRS` blocks (candidate word, casefolded term) pairs: a fuzzy window that contains the word never matches that term, so entries are per word. It covers drive/driver and four IDE collisions (IDE's Metaphone code is shared by ordinary words): "idea" 0.944, "I die" 0.941 (seen when Whisper transcribed an MP3 re-encoding of test_audio1), "id" 0.919 and "idle" 0.905 (both common in tech-support speech). It affects fuzzy scoring only; `eye dee ee` still resolves to IDE through acronym_map/letter_composed. Deliberately not blocked: "I dye" (0.905), not realistic tech-support vocabulary, so it still misfires to IDE. `tests/test_ide_collisions.py` has a control proving the guard, not a score change, is what closes them. "side" -> SSID (0.885) is the same mechanism: unrelated to any phrase, it was the single most frequent bad replacement in the coverage run (11 occurrences) and is also the one contributor to the "canonical form altered" defects above that the DP fix can't reach, because "server-side request forgery" never scores a full 1.0 exact match (hyphen in the term vs. space in speech). Four more entries came from a 32-file real-recording accuracy run, each a genuinely different word/acronym that just sounds like the term (not an inflection - see `app/morphology.py` below): "print"/"printer" 0.922, "IPS"/"IPsec" 0.882, and "to"/"access port" + "to"/"access point" 0.909/0.895 (blocking only one left the dictionary's other "access "-prefixed term exposed as the new best score - both must be blocked together). Deliberately NOT added despite also surfacing there: "catch"/"cache" (0.913) - `tests/batch_cases.py` has an existing, deliberately-authored true positive for it ("clear the browser catch" -> "...cache"), so this is genuinely context-dependent, the same irreducible ambiguity as "read"/"RAID" (a confirmed true positive in `test_audio2`, also never blocked). "restart"/"restore" 0.873 was added last, as a permanent, threshold-independent guard for one of the two ORIGINAL false positives that justified raising the threshold to 0.88 in the first place - see the threshold-lowering investigation immediately below for why it was added and why the threshold itself did not move.
- `app/morphology.py::is_ordinary_inflection(candidate, term)` is a general guard, checked alongside `NEVER_MATCH_PAIRS` in `_best_fuzzy_match`: refuses a fuzzy match when the candidate is not a phonetic corruption of the term at all, but the term itself with an ordinary English inflectional ending Mozhi's dictionary doesn't carry a separate entry for ("client's" -> client, "crashes"/"crashed" -> crash, "containerized" -> container, "ticketing" -> ticket, "backed up" -> backup) - correcting these discards grammar the speaker said correctly and was raising WER. Strips one closed-class inflectional suffix (`'s`, `s`, `es`, `ed`, `ing`) plus, as a deliberate scope call, the `-ize`/`-ise` verbalizing family (common and productive in this domain: containerize, virtualize, serialize...). Same word count only, with one exception for a phrasal verb fusing into a compound noun ("backed up" -> backup) that fires only when stripping the first word's inflection was actually necessary - so it can never interfere with a genuine STT segmentation fix like "fire wall" -> firewall (needs zero stripping). Never fires when candidate already equals term case-insensitively (`ram` vs `RAM` must still get case-corrected). Deliberately has NO bare trailing-"s" rule: it looked appealing (would also catch "credential"/"credentials") but the full-dictionary coverage test showed it wrongly blocked genuine corruptions of words that just happen to end in "s" as part of their spelling (`addres`/address, `cvs`/CVSS, `acces`/access, `los`/loss) - removed on that evidence. `tests/test_morphology.py` covers both this module and the four new `NEVER_MATCH_PAIRS` entries above, including the "why not `catch`/`cache`" and "why not bare -s" pins.
- Short acronyms that collide with English words (SATA, STP, DDoS, IDS, PAT, HSTS, IPS) are matched only via the exact acronym map. Do not add them to the dictionary expecting fuzzy matches. `letter_composer.COMPOSITION_EXCLUDED` (G4) enforces this on the composition path explicitly, so adding one to `domain_terms.json` cannot silently make it composable.
- Letter composition gates, all in `letter_composer.py` and all module-level constants for ablation: G1 `MIN_ACRONYM_LETTERS = 3` (2-letter runs like "are you" collide constantly); G2 exact dictionary match via `dictionary.get_acronym_index()`; G3 `REQUIRE_UNAMBIGUOUS = True` (at least one letter heard as an unambiguous sound such as "ess"/"dee"/"em", which is what stops "I owe a" → IOA); G4 the exclusion list; G5 punctuation (below). G3 makes acronyms spelled only with ambiguous sounds (ARP, IRP, and others) unreachable by composition; the fix for a real recording is a hand entry in `ACRONYM_PHONETIC_MAP`. Spoken digits and acronyms containing digits or dots (WPA2, IPv4, X.509, ...) are out of scope for composition. G5 exists because `tokenize()` drops punctuation ("Go see Em, Dee, be nice" would otherwise spell CMDB): the pipeline passes `tokenizer.separators()` gaps to the composer, a run ends at any of `. ! ? ; :` (`HARD_BREAK_CHARS`), and the separators between consecutive letters must be **uniform**. It is deliberately not "any comma breaks the run": "ess, ess, dee" and "vee-ell-ay-en" must still compose, and `tests/test_letter_composer_punctuation.py` pins that (mutation-tested against the naive rule). Known residual: a uniformly comma-separated run of names ("Em, Dee, are") is structurally identical to a comma-spelled acronym and still composes MDR (strict xfail in `tests/test_letter_composer_adversarial.py`); mixed separators ("vee ell, ay en") and periods between letters stop a composer-only acronym (pinned as documented limitations). Whether Whisper actually writes commas inside spelled-out acronyms is unconfirmed: the only two saved transcripts contain no runs of letter-sounds longer than one token.
- `FUZZY_STOPWORDS` does not apply to composition (the composed branch runs before that check on purpose): the guard protects fuzzy scoring only, and composition does none. Do not "fix" this.
- The scorer also scores a space-removed candidate against fused single-word terms ("mother board" vs "motherboard").
- The metaphone signal sorts per-word codes so it is word-order invariant.

**Data.** `data/domain_terms.json` holds `{term, category, is_acronym}` entries and is loaded once via `lru_cache` in `dictionary.py`. `acronym_map.py` must stay in sync with the acronyms in that file, and entries are added only from real STT failure recordings, not guessed. `letter_composer` is the opposite in kind: its coverage is derived from the `is_acronym: true` entries (via `dictionary.get_acronym_index()`), so it grows with the dictionary and needs no per-acronym entries. The Docker image bundles `data/`.

**Tests.** `tests/batch_cases.py` holds hand-written (input, expected) pairs (34 at last count) shared by the batch test, the latency benchmark, the comparison benchmark and `scripts/no_model_inference_proof.py`. Editing it changes all four, and it changes what the corpus measures: latency numbers taken before and after an edit are not comparable. `tests/test_letter_composer.py` covers the composer (each gate has a control that flips it). No batch case is xfailed. The two former xfails are closed: "idea" vs "IDE" with NEVER_MATCH_PAIRS, and "restart" vs "restore" (0.873) - originally by the 0.88 threshold alone (missed by only 0.0074), now ALSO by a permanent `NEVER_MATCH_PAIRS` entry (defense in depth; see below and `tests/test_batch_cases.py`). The old xfail was applied imperatively via `pytest.xfail()` inside the test, which hides a case from ever running; prefer `@pytest.mark.xfail(strict=True)`. Do not raise the threshold further: it would break the real match "catch" → "cache" (0.913). **Do not lower it either**: `DEFAULT_THRESHOLD = 0.88` was investigated and confirmed as the floor. A drop to 0.83 was tried (guarding "restart"/"restore" first) and looked safe on the two originally-studied cases, but a systematic sweep of all 319 terms against a 10k-word common-English list found 257 NEW word/term pairs clear 0.83 while staying below 0.88 (`app`/API, `access`/"access port", `pass`/passkey, `IP`/IPv4, `is open`/ISP, `escalate`/escalation, and more) - guarding all of them would mean blocking pairs never verified against real speech, violating this project's own standard for when a guard is justified. Reverted to 0.88; the investigation and a representative sample of the 257 are pinned in `tests/test_threshold_investigation.py` so a future casual re-attempt fails loudly instead of silently reopening them. `van` → WAN (0.706) is a **permanent, accepted limitation** of the current scorer/threshold - documented, not being worked on; no threshold this investigation found workable gets anywhere near it. Remember that WER cannot see a wrong domain term being injected: on the MP3 transcript the "I die" -> "IDE" misfire lowered the word error count by one (two wrong words collapsed into one), so closing it raises WER there while removing a false term. `tests/test_no_network.py` patches `socket.socket` to prove no network use, and is a regression guard for the no-inference proof.

## Dataset scope (intentionally scoped, don't "fix" this)
STT failure data comes from ~6–7 speakers (team plus a few volunteers), deliberately scaled back from an earlier 10–15 speaker plan. The dictionary currently has 319 terms (`tech_support` domain). Read the count from `data/domain_terms.json` and never inflate numbers in comments, docs or output.

## What "done" looks like for benchmarking
Every latency/accuracy claim must be backed by a script output artifact in `reports/`, not a number printed in chat. To prove latency, accuracy or no-inference, run the matching script in `scripts/` and write the result to `reports/`. Do not write a new ad-hoc benchmark unless the existing ones don't cover the case. Use `time.perf_counter()`/`cProfile` for latency. For accuracy, use a documented WER calculation and state whether it is character or word level. Always show the generative baseline next to Mozhi's numbers (`comparison_benchmark.py`). `reports/comparison_benchmark_blocker.md` holds the free-tier HF setup notes and the current measured Mozhi latency (24.66 ms mean / 38.25 ms p99, per `reports/latency_benchmark_letter_composition.txt`), so check it first for the comparison condition. That figure is for the 319-term dictionary, up from the original 76-term baseline (fuzzy scoring cost scales with term count), with letter composition included; the composer adds negligible overhead (~0.007 ms per sentence for the whole pre-pass including punctuation handling, measured directly; see the addendum in that report). Quote that figure with its corpus: the 34-sentence batch averages about 6 words (max 9), and correction latency grows with transcript length, so a natural 14-17 word spoken sentence takes several times longer than the batch mean. The live demo shows the per-call figure together with the transcript's word count for this reason. A `reports/` artifact of latency versus sentence length does not exist yet.
